# Connect your agents and choose how Atman uses them

T-860 · Sol strategic planner · 2026-09-13 · implementation handoff

Atman should discover the tools a person already uses, help connect them, and respect their usage preferences. Installation, account access, remaining allowance, and teammate wake are four separate capabilities. An installed CLI is not proof that its account can run work.

This document defines the requested flow and implementation graph. The wizard and quota adapters are not implemented by this planning ticket. The operator-authorized Claude settings repair described below has been applied on this Mac.

## Onboarding flow for the local app and `atm`

1. **Choose the workspace.** Connect an existing board if present. Show its objective and team; never reset it or replace leadership as a side effect. Fresh users name their team and enter one objective with a success criterion.
2. **Find your agents.** Probe catalog executables on PATH and user-selected paths with bounded, safe version/help commands. Resolve aliases such as `agent`/`cursor-agent` to one provider entry. Show Found, Not installed, or Could not check. Copy: “We found these agents. Do you use another one?” Offer supported providers, a custom executable, or remote bridge. Custom executables require explicit trust before invocation.
3. **Add another agent.** For each selected missing provider, show the official install source, target version, prerequisites, disk location and command before the user chooses Install. Support manual install and Skip. Re-scan after installation; report failure and retry without restarting the entire flow. Install no unselected provider; make no global shell/config changes implicitly. Workers must verify each install recipe against current official docs before implementing it.
4. **Connect accounts.** Run the selected provider's native browser/device login. Atman observes completion or offers Retry/Connect later, while keeping credentials in the provider's store. Show Account connected separately from Quota available and Teammate wake tested. Never treat an offline/network failure as proof that the password or subscription expired.
5. **Choose usage.** Ask “Which agents should Atman use?” For each account, let the user enable it, pick allowed models, priority and concurrency, choose how much observed allowance to reserve, and set an optional daily paid-spend cap. Defaults: no paid overages, no automatic credit redemption, one new worker at a time, alerts before allowance is low. Offer Wait for reset, Use another enabled agent, or Ask me on depletion. Unsupported quota offers user-reported allowance or Ask before starting; such permission is not a fabricated quota reading. Do not request an artificial dollar valuation for a subscription window.
6. **Connect teammates.** Choose On-demand task messages or a persistent session that may react to authorized team messages. Ask “Can teammates wake this agent?” Explain the provider's effective inbound control and account/host scope. Display the exact setting change and preserve existing custom hooks, permissions and status line. A single decision covers the user's approved scope; do not keep asking every turn. Register a unique runtime ID and stable role without inheriting the parent's session or canonical CoS identity.
7. **Test the connection.** Use an explicit, user-approved small test message with a nonce. Display Queued, Held for approval, Delivered, Acknowledged, or Work started according to actual evidence. Zero-keystroke wake requires the receiver to acknowledge without operator intervention; socket write or inbox appearance alone is insufficient. Explain any required attach/reconnect/provider limitation and allow manual mode.
8. **Start one useful task.** Show the objective and first eligible task. A dependent task releases only after independently accepted predecessor completion. Keep agent, quota source, remaining window, last checked time and next action visible alongside progress.

This wizard belongs in the existing local app work (T-810), with auth/reconnect reused from T-687 and live messaging acceptance reused from T-818/T-857. Public Vercel onboarding introduces this local connection flow; it does not expose the user's private machine board or native credentials.

## Claude incoming messages: applied repair and product requirement

The operator explicitly requested machine-wide unattended incoming messages. On this Mac, `~/.claude/settings.json` now contains `"crossSessionInbound": "accept"`. Saved original: `settings.json.bak-sol-t860-20260913-143224`; parsed before/after equality verifies every other setting preserved. This user configuration is not checked into the repository.

[Claude's native messaging documentation](https://code.claude.com/docs/en/cross-session-messaging) defines accept/hold/refuse. Without an explicit value, permission-mode classes affect whether a message is held. `accept` delivers peer messages; it does not approve the receiving session's tool permissions. A project/local refuse or higher-priority managed/launch setting can still override user settings. The installed version exceeds the documented Mac version requirement. Native messaging is not interchangeable with Atman's external socket bridge.

Onboarding should inspect applicable settings and explain the effective result, not merely detect this user key. Offer a narrowly scoped persistent-worker launch setting when only those workers are approved; offer a global change when the operator explicitly chooses machine-wide behavior. Do not set bypass permissions to enable messaging. Do not allow one peer message to stand in for human permission to alter configuration. Preserve custom hooks and existing status-line output, and show a reversible change with its scope.

If Atman lacks permission, the provider forbids agent-authored changes, or the user prefers manual setup, alert the user instead of looping on failed writes. Show the file or provider settings screen, exact change, effective override if present, and buttons “Open settings”, “I changed it — test again”, and “Use manual mode”. Claude copy: “Incoming teammate messages are held for approval. To receive them unattended, set crossSessionInbound to accept for the sessions you choose.” Never call the connection complete merely because the user dismissed the alert. A managed restriction needs an administrator rather than instructions to bypass it.

CEO and CoS were asked on T-860 to exchange nonce `sol-t860-1432` without keystrokes and distinguish inbound-policy success from the T-857 wire-protocol/receipt repair. CLI reported `woken` for both recipients, which is transport-reported and not independent proof of execution. Their actual acknowledgements are still required.

Other adapters need capability-specific treatment: Codex authenticated app-server resume; Cursor supported persistent-session transport; Agy/remote/Grok supported bridge or honest manual mode. Test idle and active sessions, provider deny/hold, missing endpoint, reconnect, and unique worker identity. Never emulate wake by launching a new paid CLI invocation and labeling it a persistent-session resume.

## Quota and preference contract

Store sanitized snapshots outside raw messages: provider, opaque account/billing scope, source, support status, observed timestamp, freshness, and a list of buckets/windows. Each window has provider ID, unit, usage or remaining value, duration and reset when known. Model-to-bucket mapping is optional and evidence-backed. Missing fields stay null. Separate account auth errors, unavailable provider, exhausted allowance, stale observation and unsupported API.

For verified percentages, remaining is `100 - used`; for a verified Agy fraction, percentage is `100 * remaining_fraction`. Reject invalid/out-of-range values. No averaging five-hour and weekly percentages. Multiple seats sharing an account consume one observed allowance, not duplicated budgets. A reserve applies separately to every applicable known window. A future reset timestamp alone does not authorize work; refresh or show unknown after the snapshot expires.

A reserve is an admission/alert preference, not a guarantee: an unknown next-task cost may overshoot it. Existing workers finish or checkpoint according to the user's policy; no unsolicited kill. Paid-spend caps need provider enforcement or explicit labeling as an Atman admission control, with unknown cost routed to Ask rather than claiming a hard monetary guarantee.

Collectors use provider-native reads and normal-session events, not LLM polling. Cache refreshes, bound timeouts and back off failures. Keep only allowlisted quota fields: no tokens, cookies, emails, transcript contents, messaging credentials or raw arbitrary status-line payload. Subscription preferences are account-scoped; board role/context and runtime IDs remain separate. For providers without a documented path, manual input is explicitly user-reported with an expiry, and does not satisfy measured efficacy/cost claims.
